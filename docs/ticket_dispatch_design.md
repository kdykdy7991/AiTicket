# 工单分派设计（判断层级 + 两张解耦表）

> 事实来源：
> - 流程骨架：《客户问题处理流程 V0.85 20260917》（单页流程图，7 阶段）
> - 分类与责任人：《问题分类 V0.21 20260929》《责任部门&责任人.docx》
> - 业务确认（2026-09-30 对话）：分派规则是规定好的流程，不是处理人自由选择；条件/优先级机制不需要。
>
> 本文替代同目录早期草稿中的 condition/priority 设计——**已废弃**。

---

## 1. 流程骨架（V0.85 七阶段）

```
诉求受理 → 问题判断 → 工单分派 → 问题处理 → 工单回访 → 工单归档 → 复盘总结
```

| 阶段 | 内容 |
|---|---|
| ① 诉求受理 | 渠道：400热线 / 微信服务号 / 内部流转；判断事件紧急程度、身份验证 |
| ② 问题判断 | 按**判断层级**逐级判定分类（见 §2），每一级由规定好的判断人执行 |
| ③ 工单分派 | 分类落位后，按分类的**部门链**派单（纯配置，见 §3） |
| ④ 问题处理 | 各部门固定动作：跟进结果回填 / 出具发票 / 执行变更 / 填写根因&方案；硬件故障特有：故障排查→是否寄回→(是)申请暂缓→完成寄修 /(否)致电反馈 |
| ⑤ 工单回访 | 接收工单返回结果 → **是否解决？**（否→退回重新处理，循环回④）→ **是否满意？**（否→收集不满意原因；是→闭环） |
| ⑥ 工单归档 | 闭环 |
| ⑦ 复盘总结 | 梳理高频问题更新客服知识库；痛点反馈产品/研发/业务；优化服务流程 |

**核心认知**：
- "问题判断"和"工单分派"是两个独立阶段：判断是**人工分诊**（按规定层级），分派是**配置驱动**（按分类查部门链）。
- 分类树本身就是路由键——**没有 condition、没有 priority**，L 级判完 → 查该级分类的链 → 派单。
- "再次分派"不是处理人自由决定：判断人只能把分类细化到下一级，**下一步派给谁由链规定**。

## 2. 判断层级（谁判断、判到哪级）

| 判断级 | 判断人 | 判定范围 | 落位后 |
|---|---|---|---|
| **第 1 级** | **客服**（建单时） | 咨询 / 服务投诉 / 业务运营 / 业务保障 四大类（含咨询、投诉、运营的细分，见 §4） | 按该分类的链派单 |
| **第 2 级** | **售后**（业务保障类专属） | 应用平台 / 星座大系统 / 终端软件 / 硬件故障 四选一 | 按 L2 细分后的链派单；**星座大系统除外**（还有第 3 级） |
| **第 3 级** | **星座大系统负责人** | 核心网系统 / 测运控系统 / 卫星系统 三选一 | 按 L3 细分后的链派单（判断结束） |

**判断级 = 分派深度**，直接回答"有的需要多级分派，有的不需要"：

```
客服 ──判──> 业务保障 ──交张华指派──> 售后人员 ──判──> 应用平台 ──派──> 平台运维组 ──处理
                                          └─ 终端软件 ──派──> 终端研发   ──处理
                                          └─ 硬件故障 ──派──> 售后(自己) ──处理
                                          └─ 星座大系统 ──派──> 星座大系统负责人 ──判──> 核心网/测运控/卫星
                                                                              └─派──> 软件开发组 / 测运控组 / 整星产品
```

- 应用平台、终端软件、硬件故障：**2 级判断**落位；
- 星座大系统下三个子类：**3 级判断**落位；
- 咨询、服务投诉、业务运营：客服一步判定（无中间判断部门）。

**"分诊"动作的语义**（工单系统需要支持）：

| 项 | 内容 |
|---|---|
| 动作 | 当前判断人把工单分类细化一级（如 业务保障 → 应用平台） |
| 触发 | 分类更新 → 系统按新分类的链重新派单 → owner 切换到链的下一部门 |
| 权限 | 仅该级的规定判断人 |
| 约束 | 分类只能按树的父子关系细化，不能跳级、不能凭空改 |

## 3. 两张表（解耦设计）

### 表 A：分类 → 部门链（dispatch_chain）

只存"分类落位后要依次过哪些部门"。**判断节点所在的部门写进链里作为下一步**；业务保障细分类在专业处理后增加售后致电反馈节点，其 `stage` 为 `phone_feedback`。这一步与之后的客服回访不同；客服回访仍是框架级环节，不进分派链。**没有 condition、没有 priority**。

```yaml
dispatch_chain:
  id:           int PK
  category_id:  int FK → ticket_categories.id    # UNIQUE：一个分类一条链
  steps:        json[]                           # 纯部门代称，顺序执行
  enabled:      bool
  note:         str
```

steps 元素：

```json
{ "order": 1, "department_code": "售后" }
```

匹配规则：**分类 → 唯一的链 → 按 steps 顺序推进**。工单建单/分诊时按分类查链，展开为工单的链快照（`dispatch_chain_snapshot`），后续推进按快照执行（规则后续修改不影响在途工单）。

### 表 B：部门 → 人员（department_member）

只存"部门代称对应哪些人、扮演什么角色"。

```yaml
department_member:
  id:               int PK
  department_code:  str                 # 与表 A 的 steps 对齐
  user_id:          int FK → users
  member_role:      dispatcher | handler | both
  is_active:        bool
  effective_from:   date
  effective_to:     date                # 调岗/离职填截止，不删行（审计可回溯）
  note:             str
```

- `dispatcher`：受理分派（pending→open）的人；
- `handler`：执行处理动作的人；
- 同部门多人时由 dispatcher 在 UI 指定，链里不关心是谁。
- **改人不改链**（人员变动只动本表），**改链不改人**（流程调整只动表 A）。

## 5. 三类特殊处理

### 5.1 值班组部门化（一般投诉）

"值班主管"不作为角色，**实体化为部门代称 `值班组`**，按班次在 department_member 里维护：

```yaml
- department_code: 值班组
  user_id: 王耀宗
  effective_from: 2026-09-30 早班
  effective_to:   2026-09-30 晚班
  member_role: handler
```

好处：dispatch_chain 全表统一为"部门 → 部门"，无角色特例。

### 5.2 重要/重大投诉走 escalation_policy

"相关部门负责人""分管领导"是**动态角色**（取决于投诉涉及哪个部门），不进 department_member，沿用既有 `complaint_escalation_policies` 扩展：

| 投诉等级 | 机制 |
|---|---|
| 一般 | dispatch_chain → 值班组 |
| 重要 | escalation_policy：工单涉及部门的 leader |
| 重大 | escalation_policy：leader → 分管领导（升级链） |

dispatch_chain 里重要/重大两条不配 steps，由投诉流程按等级走 policy。

### 5.3 星座大系统负责人

- 第 3 级判断人；既有业务文档约定"先用占位账号，角色设计阶段统一整理"。
- department_member 配置：`星座大系统负责人` → 占位账号（待正式账号后只改本表）。

## 6. 与现有系统的关系（现状 → 目标）

| 目标 | 现状 | 动作 |
|---|---|---|
| 分类树（不限深） | `ticket_categories` 单表自引用，已放宽深度 ✅ | 复用 |

| 投诉升级 | `complaint_escalation_policies`（SLA 倍数 + required_role） | 扩展 escalation_chain 字段 |

## 7. 实施步骤

1. **建表**：`dispatch_chain`（category_id UNIQUE + steps）+ 扩展 `department_member` 生效区间字段；
2. **Seed**：按 §4 两张表灌数据（含值班组、星座大系统负责人占位）；
3. **分诊动作**：state_machine 增加 `refine_category`（仅规定判断人；分类只能细化一级；触发按新链派单）；
4. **链快照**：建单/分诊时展开链写入 ticket，分派按快照推进；
5. **投诉分流**：一般→链；重要/重大→escalation_policy；
6. **建单校验调整**：业务保障类允许二级为空；
7. **清理**：`category_routing_rules` 退居只读/下线。

| 10 | 复盘总结（第⑦阶段） | 完全没有 | 范围外，后续设计 | 不在本期 |

### 8.3 实施顺序

1. **数据层（无破坏性）**：新建 `dispatch_chain` + seed 灌 §4 链数据；`user_skill_groups` 加生效区间列；
2. **基线**：跑现有单测确认不破坏；
3. **行为层**：分诊动作进状态机 → 建单校验放宽（业务保障类二级可空）；
4. **小改**：套餐查询预置即时办结、投诉 escalation_chain、不满意度原因字段；
5. **清理**：`category_routing_rules` 退居只读/下线。

新表 vs 原地改造：**新建 `dispatch_chain`，旧表双轨过渡后下线**（改动隔离，可回滚）。
