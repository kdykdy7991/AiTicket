# POC 前后端并行开发与联调清单

## 目录所有权

| 开发者 | 可直接修改 | 原则上不修改 |
| --- | --- | --- |
| 后端开发 | `backend/**` | `frontend/**` |
| 前端开发 | `frontend/**` | `backend/**` |
| 双方 | `docs/poc/**` 仅用于修正共同契约，修改前先同步 | — |

## 新建与附件调用顺序

统一采用“先建草稿、后传附件、最后提交”：

1. `POST /tickets`，携带 `is_draft=true`，取得工单 ID。
2. `POST /tickets/{id}/attachments` 上传现场材料；无附件时跳过。
3. `POST /tickets/drafts/{id}/submit` 正式提交，进入 `pending_approval`。

不得另外实现一套 multipart 正式建单接口。

## 联调检查点

1. **契约检查点：** 后端完成角色、状态、优先级、Schema 和 OpenAPI；前端完成类型和 Mock，双方逐项核对编码。
2. **主流程检查点：** 暂不处理通知和报表，先从售前提交一直走到批准人复核闭环。
3. **异常流程检查点：** 联调权限拒绝、必填校验、并发冲突 `409` 和三条退回路径。

## 合并约定

- 后端分支先合并数据库迁移和 API 契约，前端分支随后解决接口联调差异。
- 任一方需要修改状态、角色、字段名或动作编码时，必须先修改开发总约定并通知另一方。
- 不通过前端临时字段映射掩盖接口命名不一致。
- 两边提交中不要包含对方目录的格式化或无关改动。

## 最终联调验收

- 使用售前、批准人、专项小组、分系统、质量五个账号完成全流程。
- 管理员可代操作，但不出现在业务角色选择器和责任人选择器中。
- 页面和 API 均不接受旧角色、旧状态、旧优先级。
- 退回原因、修订记录、状态日志和闭环批准信息完整可追溯。
- 前端 `npm run build` 与后端 `pytest` 同时通过。
