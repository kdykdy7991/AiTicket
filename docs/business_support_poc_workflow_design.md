# 业务保障借鉴 POC 主流程：早期范围分析

> 本文保留初期讨论记录，不作为当前实施方案。已确认的范围仅为“业务保障 → 星座大系统”，以 [星座大系统流程方案](constellation_poc_flow_design.md) 为准；本文关于其他分类、质量评审、旧单迁移的建议均未纳入此次实施。
>
> 2026-10-26 静态代码分析。POC 事实以 `/home/hello/workspace/Poc/backend/app/domain/poc_workflow.py`、`services/poc_workflow.py` 为准；本仓库事实以 `backend/app/services/state_machine.py`、`node_context.py` 和分派链为准。

## 1. 两边实际流程

| 环节 | POC | 本仓库业务保障 | 迁移判断 |
| --- | --- | --- | --- |
| 建单 | 售前草稿→正式提交→指定批准人初审 | 客服草稿/建单，判到业务保障，进入待受理 | 借鉴“草稿与正式提交分离”；保留客服受理主体。是否增加主管初审需业务确认 |
| 判断与路由 | 专项小组确认，可选择多个分系统及负责人，按部门拆成独立工单 | 售后负责人指派人员；售后分诊二级，星座大系统负责人再分诊三级；按分类部门链自动路由 | 保留现有逐级分类和固定部门链；可借鉴“指定责任人、确认记录”。多部门分单单独设计 |
| 响应措施 | 分系统负责人提交初步排查及临时措施 | 专业处理节点按表单提交，链推进 | 在专业处理节点增加“响应措施制定”业务子阶段和表单 |
| 措施效果确认 | 创建单的售前确认 | 当前没有独立确认节点；末端售后致电反馈，之后客服回访 | 增加客服/诉求人代理的效果确认，明确与售后致电反馈和最终客服回访的区别 |
| 分析验证 | 分系统负责人提交根因、整改及条件字段 | 处理表单已有根因/方案，缺少独立的二次分析阶段 | 借鉴条件校验与二次提交；尽量复用现有版本化节点表单 |
| 质量评审 | 质量角色验证并通过 | 无独立质量角色审批 | 增加可配置质量责任人和评审动作；不能直接照搬 POC 角色编码 |
| 闭环 | 创建人闭环确认→原批准人终审→关闭 | 售后致电反馈→`resolved`→客服回访/归档；不认可或不满意可退回重办 | 复用当前客服回访/归档；是否增加主管终审需确认，避免双重同义确认 |
| 退回 | `returned` + `return_to_state`，指定节点修订后继续 | `returned` 主要用于待受理退回；处理中/已处理退回通过状态边和 checkpoint | 为业务保障增加明确的退回目标和责任人，保留现有其他分类状态含义 |
| 时限 | 从进入 `planning` 到提交响应措施，P0–P3 | 业务保障 P1–P4，整轮从正式建单到最后处理节点，转派/暂缓不重置 | 两种时钟用途不同；保留现有解决 SLA，另增响应措施时限指标 |

POC 还有售前分单专属短流程、按多个分系统复制 N−1 张工单、动作版本冲突检查、节点附件、流程日志和催办。它们属于主流程配套能力，但并非每一项都适合首批上线。

## 2. 推荐目标流程

```text
客服建单 → 售后指派/分诊 → 专业部门确认并制定响应措施
         → 客服确认措施效果 → 专业部门分析验证
         → 质量评审 → 售后致电反馈 → 客服回访/归档
```

星座大系统继续由其负责人完成三级分诊；硬件故障继续遵守现有售后处理和寄修逻辑。专业部门与责任人由当前分类链和部门成员配置确定。效果确认由客服承接（客户反馈由客服记录），而非将 POC 的“创建售前”直接映射成售后。质量评审只评价技术验证材料；售后致电反馈记录对客户的解释，客服回访判断是否认可和满意。这样三个确认点各有不同职责。

建议把业务保障流程作为**分类限定的工作流实例**，与全局工单的 `state` 分开：全局状态继续服务列表、统计和其他分类；新增 `workflow_kind=business_support`、`workflow_stage`、`workflow_version`、`stage_owner_id`、`return_to_stage` 等业务保障字段，或等价的独立实例表。正式节点包括 `triage`、`measure_planning`、`measure_confirmation`、`analysis`、`quality_review`、`phone_feedback`、`customer_closure`。`pending/open/resolved/archived` 只在对应阶段边界同步，所有变化仍经过本仓库唯一状态执行入口；不能在新服务里直接写 `ticket.state`。

各阶段动作由服务端一张规则表定义：当前阶段、动作、目标阶段、允许角色、指定责任人范围、表单版本、必填条件、允许退回目标。详情页只渲染服务端返回的 `allowed_actions`，提交时服务端重算权限及前置条件。每次动作在同一事务内锁定工单、比对版本、校验表单、保存 Submission/附件关联、写状态日志及责任人快照，然后通知下一责任人。建议增加 `workflow_version` 的 409 冲突响应，借鉴 POC 的 `expected_version`。

### 退回路径

| 发起阶段 | 目标 | 重做方式 |
| --- | --- | --- |
| 响应措施制定 | 售后分诊/指派 | 修正分类或责任人，保留原路由记录 |
| 措施效果确认 | 响应措施制定 | 原专业负责人修改措施后再确认 |
| 质量评审 | 分析验证 | 原专业负责人补充根因和验证材料 |
| 售后致电反馈 | 质量评审或分析验证 | 按退回原因修订，不覆盖旧记录 |
| 客服回访不认可/不满意 | 专业处理重新开启 | 继续沿用现有新一轮 SLA 和回访闭环规则 |

退回必须填原因；日志同时记录发起节点、目标节点、动作人、当时责任人和表单快照。目标节点可直接修改并重新提交，避免额外“确认接收”空节点。允许退回目标应固定在规则表，前端不自由传任意阶段。

## 3. 可复用与必须改造的边界

- **直接复用本仓库**：分类树及 `dispatch_chain_steps` 快照、部门成员管理、售后指派/逐级分诊、节点表单的定义与 Submission、Article 附件、售后致电反馈、客服回访归档、解决 SLA 轮次、状态日志与 `apply_transition`。
- **移植 POC 的做法而非整文件复制**：`ACTION_RULES` 约束表、指定责任人范围、条件必填校验、乐观并发版本、节点时长/通知/催办、退回目标。POC 的状态码、角色码、创建人含义、P0–P3 优先级与本仓库不兼容。
- **多部门分单第二阶段处理**：本仓库的“多步部门链”是同一工单顺序经过多个部门，不能等同 POC 的“一问题分出多个独立工单”。确需并行时新增关联组 ID、父/源单关系及汇总闭环规则，决定是各分单分别归档还是全部完成后主单才可归档。复用前序附件应共享存储引用并保留来源，避免简单复制历史日志导致审计中每张分单看似亲历了尚未发生的动作。
- **表单字段**：优先在当前表单平台发布业务保障专属版本。响应措施至少记录排查结论、临时措施；分析阶段按技术/管理原因条件校验；质量阶段记录验证状态、结论、评审结果。具体必填以业务字段清单核定，不能照搬 POC 反馈表中的测试设备、固件等建单强制项。
- **SLA**：保持现有 P1–P4 整轮解决时限；另加从专业部门接单到提交响应措施的时钟和报表。两项超时分别展示，避免覆盖 `solution_deadline`。

## 4. 实施顺序和验收

1. **冻结流程口径**：确认是否需要建单主管初审和闭环主管终审、措施效果确认人、质量角色归属、售后致电反馈与回访的先后、多部门并行分单及旧单迁移策略。输出状态图、动作权限矩阵和字段清单。
2. **建工作流核心**：新增业务保障实例/阶段与动作规则；只对业务保障分类启用。加入版本检查、日志快照、退回目标和锁单事务；与全局状态执行器对接。
3. **接入节点表单及页面**：发布措施、确认、分析、评审表单；详情页显示阶段、责任人、动作和完整时间线。禁止旧 PATCH、reply、批量更新绕过新节点校验。
4. **接入提醒和双时钟**：下一责任人通知、节点停滞催办、响应措施时限；解决 SLA 保持既有轮次规则。
5. **灰度与迁移**：新建业务保障单先走新流程；在途单按当前分类、链步和状态映射，无法确定的单保留旧流程至归档，不能自动推断已完成的评审。其他分类流程保持原规则。

最低验收路径：应用平台、终端软件、硬件故障、星座大系统三级分诊各完成主流程；措施被退回、分析被退回、回访不满意重办；无权限人和并发旧版本提交失败；旧业务保障单按既定策略可继续处理；咨询/投诉/业务运营回归；响应措施时钟与解决 SLA 各自计时正确；日志和附件在每次退回重做后可追溯。

## 5. 当前需要业务拍板的四项

1. 是否把 POC 的**初审和最终批准人复核**搬进业务保障，批准人是谁；若没有明确责任人，建议首版不设这两个节点。
2. **措施效果确认**由客服根据客户反馈确认，还是由售后/业务负责人确认；建议客服记录客户意见。
3. **质量评审**是否为全部业务保障工单必经，或仅重大级别/特定二级分类；建议先全部经过，后续按规则豁免。
4. 一问题涉及多专业部门时，是否需要**并行分单**；建议首版保留顺序链，确有并行协作需求再实现分单汇总。
